# Plan: Fix Google OAuth Login Flow with Role-Based Routing

## Problem Statement

Currently, when users click "Continue with Google":
- New OAuth users without a complete profile are redirected directly to the dashboard
- The system doesn't properly check if the user's profile matches the selected tab (creator/brand/agency)
- Users don't complete the rest of the signup form after OAuth authentication

## Requirements

Based on user specification:

1. **Check the selected tab** when user clicks "Continue with Google" (creator, brand, or agency)
2. **For existing users with matching profile**:
   - Redirect them directly to their dashboard
3. **For new OAuth users (no profile)**:
   - Redirect to the appropriate signup form for the selected role
   - Email is already verified via OAuth, skip email verification step
   - User must complete remaining profile fields
4. **For users with profile but wrong tab selected**:
   - Show clear error message: "Account not found under this tab. Please try another tab."
   - Log them out to prevent confusion
   - Allow them to switch tabs and try again

## Current Flow Analysis

### Files Involved:
- `likelee-ui/src/pages/Login.tsx` - Login page with tab selection
- `likelee-ui/src/auth/AuthProvider.tsx` - Auth state management and OAuth handling
- `likelee-ui/src/auth/onboarding.ts` - Helper functions for auth intent and routing
- `likelee-ui/src/pages/ReserveProfile.tsx` - Creator signup flow
- `likelee-ui/src/pages/OrganizationSignup.tsx` - Brand/Agency signup flow
- `likelee-ui/src/auth/ProtectedRoute.tsx` - Route protection and onboarding redirect

### Current Issues:

1. **Login.tsx Line 173-189**: When no profile exists, redirects to signup but doesn't check if onboarding is incomplete
2. **Login.tsx Line 191-235**: When profile exists, only checks role match, then redirects to dashboard without checking `onboarding_step`
3. **AuthProvider.tsx Line 167-205**: `fetchProfile` creates a creator profile automatically if none exists, bypassing the signup flow
4. **Login.tsx Line 217-234**: Redirects to dashboard without checking if profile has `onboarding_step !== "complete"`

# HOTFIX: Infinite Loading Bug After OAuth Signup

## Issue Discovered (2026-04-01)

**Problem:** After OAuth authentication, new users who should be redirected to signup forms experience infinite loading instead.

**Root Cause:** In `AuthProvider.tsx`, the `fetchProfile` function doesn't explicitly set profile state when no profile is found for OAuth users, leaving Login.tsx unable to distinguish between:
- Profile fetch still in progress (should wait)
- Profile fetch complete but no profile exists (should redirect to signup)

## Technical Analysis

### The Bug Flow:

1. OAuth user logs in for first time
2. `onAuthStateChange` fires, `fetchProfile` is called with `isOAuth=true`
3. `fetchProfile` searches all tables, finds no profile
4. Line 183 condition fails: `else if (userEmail && (table === "creators" || !table) && !isOAuthUser)`
5. **No `setProfile()` call happens - profile state remains undefined/stale**
6. Login.tsx line 172: `profileResolved = initialized && (profile !== null || !user)`
7. For OAuth user: `profileResolved = true && (false || false) = false`
8. Login.tsx line 175: `if (!profileResolved) return;` **blocks forever**

### Why profileResolved Logic Fails:

```typescript
// Login.tsx line 172
const profileResolved = initialized && (profile !== null || !user);
```

This tries to detect "profile fetch complete" but can't distinguish:
- `profile === null` because fetch hasn't happened
- `profile === null` because no profile exists

## Solution

### Option A: Add Explicit Null State (Recommended)

Update `AuthProvider.tsx` `fetchProfile` to explicitly set profile to `null` when no profile found:

```typescript
// Line 222 in fetchProfile, add after the else if block:
} else if (userEmail && (table === "creators" || !table) && !isOAuthUser) {
  // ... existing auto-create logic
} else {
  // OAuth user or other case where no profile exists - explicitly set null
  console.log("No profile found for user:", userId, "isOAuth:", isOAuthUser);
  setProfile(null);
}
```

### Option B: Add Profile Loading State

Add a separate `profileLoading` state to track fetch status:

```typescript
// AuthProvider.tsx
const [profileLoading, setProfileLoading] = useState(false);

// In fetchProfile, wrap logic:
const fetchProfile = async (...) => {
  setProfileLoading(true);
  try {
    // ... existing logic
  } finally {
    setProfileLoading(false);
  }
};

// Export profileLoading in context
// Login.tsx can then check: profileResolved = initialized && !profileLoading
```

### Option C: Fix profileResolved Logic

Update Login.tsx to better detect when profile fetch is complete:

```typescript
// Instead of:
const profileResolved = initialized && (profile !== null || !user);

// Use:
const profileResolved = initialized && (
  profile !== null || // Profile exists
  !authenticated ||   // Not logged in
  (authenticated && user && /* some way to know fetch is done */)
);
```

## Recommended Fix: Option A

**Reasoning:**
- Simplest change with least side effects
- Explicitly sets the expected state
- Matches React best practices (always call setState)
- No API changes needed

**Implementation:**

1. **File: `likelee-ui/src/auth/AuthProvider.tsx`** (line ~222)
   ```typescript
   } else if (userEmail && (table === "creators" || !table) && !isOAuthUser) {
     // Profile missing in profiles table, create it (only for email/password creators, NOT OAuth)
     // OAuth users should be redirected to signup forms instead
     console.log("Profile missing, creating new profile for:", userId);
     // ... existing upsert logic ...
   } else {
     // No profile found and not auto-creating (OAuth user or other case)
     console.log("No profile found for user:", userId, "isOAuth:", isOAuthUser);
     setProfile(null);
   }
   ```

2. **Add logging** to help diagnose future issues:
   ```typescript
   console.log("Profile fetch complete", {
     userId,
     foundProfile: !!data,
     isOAuthUser,
     table,
   });
   ```

# 🔴 CRITICAL BUG FOUND - Root Cause Identified!

## Date: 2026-04-01 19:45

## The Real Bug

**Location:** `Login.tsx` line 340

```typescript
// Show loading state when redirecting or when authenticated
if (isRedirecting || authenticated) {
  return ( /* Loading spinner */ );
}
```

**Problem:** This condition shows loading spinner for **ALL authenticated users**, not just those being redirected!

## Bug Flow

1. OAuth user logs in → `authenticated = true`
2. **Line 340 renders loading spinner IMMEDIATELY** ✅ (before profile is even fetched)
3. AuthProvider fetches profile in background
4. Profile set to `null` (OAuth user, no profile)
5. useEffect detects no profile, tries to navigate to signup
6. **BUT THE COMPONENT IS STUCK IN LOADING RENDER** 🔴
7. Navigation never happens → infinite loading

## Why Logs Alone Won't Show This

The logs will show:
```
[AuthProvider] setProfile(null) ✅
[Login] profileResolved: true ✅
[Login] Redirecting to signup: /CreatorSignupOptions ✅
```

But the **render function** (line 340) blocks the redirect from ever displaying because it shows loading for authenticated users!

## The Fix

**Option 1: Only show loading during active redirect (Recommended)**

```typescript
// Login.tsx line 340
// OLD (buggy):
if (isRedirecting || authenticated) {

// NEW (fixed):
if (isRedirecting) {
  return ( /* Loading spinner */ );
}
```

**Option 2: Show loading only while profile is being resolved**

```typescript
// Login.tsx line 340
const profileResolved = initialized && (profile !== null || !user);
if (isRedirecting || (authenticated && !profileResolved)) {
  return ( /* Loading spinner */ );
}
```

**Option 3: Show loading only for authenticated users without initialized state**

```typescript
// Login.tsx line 340
if (isRedirecting || (authenticated && !initialized)) {
  return ( /* Loading spinner */ );
}
```

## Why This Wasn't Caught Before

The `setProfile(null)` fix we added IS working correctly. The problem is the render logic runs BEFORE React can process the navigation triggered by the useEffect.

React render order:
1. Render function executes (line 340 check happens)
2. Returns loading spinner
3. useEffect runs AFTER render
4. Navigation triggered but component already rendered loading
5. Next render → checks line 340 again → still authenticated → loading again
6. **Infinite loop because line 340 never allows the redirect to render**

## Recommended Solution: Option 1

Remove `authenticated` from the loading condition entirely:

```typescript
// Login.tsx line ~340
- if (isRedirecting || authenticated) {
+ if (isRedirecting) {
    return (
      <div className="min-h-screen bg-gray-50 flex items-center justify-center p-4">
        {/* Loading spinner */}
      </div>
    );
  }
```

**Why this works:**
- `isRedirecting` is explicitly set to `true` when we want to show loading
- We set it in the useEffect before navigating (line 205)
- This gives precise control over when loading shows
- No more blocking all authenticated users
