# Plan: Database Migration Refactoring (#296)

## Problem Summary

The supabase/migrations/ directory has 129 migration files with severe organizational issues:

1. **17 duplicate sequential migration numbers** (0005, 0006, 0007, 0010, 0012, 0013, 0014, 0015, 0020, 0022, 0035, 0036, 0039, 0040, 0041, 0042, 0044)
2. **Mixed naming conventions** - sequential (0001_) AND date-based (2026-03-04_) AND mixed date formats (20260115_ vs 2026-01-19_)
3. **Duplicate table definitions** across migrations:
   - scouting_prospects/trips/events/submissions in both 0002_ and 20260115_
   - brand_activity_events in 2026-03-17_ and 2026-03-21_
   - agency_payout_requests in 0036_ and 0044_
   - agency_payment_link_transfers in 0040_ and 2026-03-23_
4. **No concern separation** - unrelated features crammed into one migration, related features scattered
5. **No modularity** - agency tables across 30+ files, creator/talent across 20+, booking across 15+
6. **Duplicate functions/triggers** - handle_payout_request_status_change defined differently in 0036 vs 0044
7. **Broken transaction boundaries** - 0001_core_profiles.sql has COMMIT then ALTER TABLE without BEGIN
8. **Gap in numbering** - jumps from 0045 to 0056

## Critical Constraint

**The application is already deployed.** Any refactoring must NOT break existing databases. Supabase tracks applied migrations by filename in supabase_migrations.schema_migrations - renaming or deleting files would cause them to re-run or be lost track of.

## Strategy: Two-Track Approach

- **Track A - Safe Cleanup**: Documentation, convention guide, mark legacy migrations. Zero risk to deployed DB.
- **Track B - Fresh Schema Squash**: Consolidated baseline migration for new environments only. Existing deployments continue using historical migrations.

## Phase 2: Naming Convention and Future Standard

### 2.1 Establish new naming convention
For all new migrations going forward, use Supabase CLI standard format:

    YYYYMMDD_HHMMSS_brief_description.sql

Example: 20260416_143000_add_brand_notifications.sql

This ensures: no duplicate prefixes, chronological ordering, machine-generated timestamps.

### 2.2 Write convention guide
Create supabase/migrations/CONVENTIONS.md documenting:
- Naming format (always use `supabase migration new` to generate)
- One migration per feature/concern
- Use CREATE TABLE IF NOT EXISTS and ADD COLUMN IF NOT EXISTS for idempotency
- Always wrap in BEGIN/COMMIT
- Never rename existing migration files
- Add comment header with purpose and related issue/ticket

## Phase 4: Mark Legacy Migrations

### 4.1 Add deprecation headers
For each superseded migration, add a header comment:

    -- LEGACY MIGRATION - Superseded by 00000_baseline_consolidated.sql for fresh installs
    -- DO NOT DELETE - Required for existing deployed databases
    -- Last verified: 2026-04-16

Do NOT delete or rename any existing migration files.

### 4.2 Categorize all 129 migrations
- **Pure CREATE**: Only creates new tables/indexes (safe to merge into baseline)
- **ALTER additions**: Adds columns to existing tables (safe to merge)
- **ALTER modifications**: Changes existing columns/constraints (careful merge needed)
- **Data migrations**: INSERT/UPDATE of data rows (must be preserved separately)
- **Function/trigger overrides**: Replaces previous definitions (keep only latest)

## Implementation Order

1. Phase 1 (audit) - no code changes, pure documentation
2. Phase 2 (conventions) - write CONVENTIONS.md only
3. Phase 3 (baseline) - create the consolidated migration file
4. Phase 4 (legacy headers) - add comments to existing files
5. Phase 5 (validation) - test both paths
6. Phase 6 (ER diagram) - create visual documentation

Each phase should be a separate PR for review safety.

## Decisions

1. **Baseline generation**: Hybrid approach - pg_dump for the base schema, then manually organize into domain sections and clean up.
2. **ER diagram**: Mermaid in markdown (renderable in GitHub, lives in repo).
3. **Migration categorization**: Automated via a Python script that parses all migration files, categorizes them, and generates the dependency map.
4. **Baseline file location**: Lives alongside legacy files in `supabase/migrations/` (Supabase CLI requires flat structure), with prefix `00000_` to sort first.
5. **Schema migrations tracking**: Need to handle `supabase_migrations.schema_migrations` entries to ensure Supabase CLI recognizes all legacy migrations as already applied when using the baseline.
